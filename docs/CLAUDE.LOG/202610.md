## 2026-10-24 B1 路徑編碼與關卡解碼（spec：docs/superpowers/specs/2026-10-24-prime-trail-design.md）

- **起因**：plan `docs/superpowers/plans/2026-10-24-prime-trail.md` Task B1（taskboard GAME-3）。C 層的生成腳本、`useGame`、儲存層、PDF 都要從 `LevelRecord` 拿到 `Level`／`Puzzle`，這層必須先有。
- **裁定（使用者）**：無（照已核准的 plan）。
- **做法**：`src/core/path-codec.ts` 與 `src/core/level-decode.ts` 都是純函式，只 import `types`／`geometry`／`primes`，不碰 Vue 和 DOM。`PathCodecError.index` 定為「出錯的位置」：在 `decodePath` 是 `dirs` 的字元索引，在 `encodePath` 是壞步起點的 path 索引；長度錯、起點不是格子這類整體性錯誤給 `-1`。這樣生成器與測試輸出能直接指到哪一步壞掉。`encodePath` 除了 plan 列的長度與相鄰檢查，也擋格子越界與重訪：這兩種輸入若能編出字串，`decodePath` 就解不回原路徑，round-trip 的保證會破。`derivePuzzle` 依質數由小到大填 givens（`start→1` 放第一個），並複製一份 `grey`，因為 `Puzzle` 會交給 composable，不希望它改到 `Level` 的資料。`parseLevelFile` 除了 plan 列的檢查，也依 spec §3.2 擋 `s` 不是邊緣格、`h ≥ 2^25`、`c` 不在 `null ∪ [1, 1000]`、`seed` 不是 32-bit 無號整數，錯誤訊息都帶 `levels[i].<欄位>`。刻意不做的有兩件：一是不強制 `count === 1000`（plan 的測試用 `count:1`，只要求跟 `levels.length` 一致）；二是不在 parse 時把每筆 `p` 解成路徑。路徑合法性留給 `decodeLevel` 呼叫時檢查，以及 C7 的題庫完整性測試。
- **守門**：測試檔 5 → 7、案數 29 → 55（`path-codec.test.ts` 12 案，含 fast-check：兩條 fixture 路徑及其反轉的 round-trip；`level-decode.test.ts` 14 案）。DoD：`pnpm typecheck` 通過、`pnpm test` 7 檔 55 案全綠、`pnpm build` 成功。

## 2026-10-24 B3 Solver：計數到 n 即停、節點預算（spec：docs/superpowers/specs/2026-10-24-prime-trail-design.md §5）

- **起因**：plan `docs/superpowers/plans/2026-10-24-prime-trail.md` Task B3（taskboard GAME-5）。題庫生成（C1）的唯一解檢查、進階 greedy 與挑戰計數都靠這支 solver，題庫與測試也用它驗證。
- **裁定（使用者）**：無（照 spec §5 與 plan 走）。
- **做法**：
  - 前處理把 start 當成 1 的 given 一起驗：given 越界、同格兩值、同值兩格、灰底與質數不符、灰底格數 ≠ 25、連續 given 距離超過數字差或奇偶不合，一律直接回 `{count:0, exhausted:true, nodes:0}`。spec 只要求距離檢查；其他幾條也都是「必無解」的必要條件，讓 C1 拿到壞題面時不會白跑預算。
  - 有了連續 given 的靜態檢查，§5.4.1 的 given 可達性只需檢查「下一個 given」（三角不等式蓋過其餘），省下每步掃全部 given。
  - §5.4.2 的質數可達性改成較強但仍必要的形式：未訪灰底格依距離排序後，第 i 近的必須在第 i 個未用質數的步數內（Hall 條件的排序形式）。它同時涵蓋 spec 的兩條（最近灰格趕得上下一質數、每個灰格都有質數趕得上），用 19 格的距離桶計數，O(25)。
  - 度數規則多一條：若 100 是 given，唯一可當終點的 avail=1 格只能是那一格。
  - 節點 = 通過 §5.3 候選過濾後實際放下的次數，預算在放之前檢查，所以 `nodes ≤ maxNodes` 嚴格成立（plan 允許 +4，實作不需要）。初始的 1 不算節點，因此「全部 given」的題面 nodes 恰為 99。
  - 達到 `maxSolutions` 就停並回 `exhausted:false`，即使剛好是最後一解：停下時無法知道後面還有沒有，照 §5.1 語意。`collect` 為真時無解也回空陣列，呼叫端不必判 undefined。
  - 連通性 BFS 照 spec 每步都做，沒有先改成「度數變動才做」：整檔測試 < 2 s，遠低於 plan 的 10 s 門檻，不需要提前最佳化。
  - 刻意不動：`types.ts`、`geometry.ts`、`primes.ts`、fixture；測試不 import 同層的 B1／B2，mask 解碼與解的合法性檢查在測試檔內自寫。
- **守門**：新增 `src/core/__tests__/solver.test.ts` 9 案（easy 唯一、{1,17} 唯一、恰 2 解且對上兩條 fixture 路徑、maxSolutions 早停、節點預算、挑戰找 2 個合法解、距離不可能題面、矛盾 given、全部 given）。`pnpm test` 由 5 檔 29 案增為 6 檔 38 案；DoD 三條全綠。
- **流程**：taskboard 派工單 agent，在 worktree `task/GAME-5` 直接實作，未再 fan out。

- **裁定（使用者）**：無（照 spec §4.1–§4.2 的規劃者決定：backbite）。
- **做法**：新增 `src/core/generator.ts`，只 import `geometry`、`primes` 與 `types`（`Rng` 由呼叫端注入），不碰 B1–B3 的模組（同層互不 import）。`backbiteStep` 依 plan 字面「選該端點的非路徑鄰接相鄰格」：先濾掉端點在路徑上的鄰居再 `rng.pick`，所以每步必定改變路徑（每個端點至少兩個格鄰、只有一個是路徑鄰居）；代價是不完全等於 Mansfield 原版「含空步」的均勻取樣，對遊戲多樣性無影響。反轉用 `subarray().reverse()` 原地做、位置用 `indexOf`，測試檔含二十多次十萬步整檔約 1 s。`randomHamiltonianPath` 的端點上限語意：在 `steps` 之後最多再做 `edgeExtraMax` 步，仍無邊緣端點即回 `null`（`edgeExtraMax=0` 表示不加步）；兩端皆邊緣時才擲 `rng.int(2)`，只有一端邊緣時不耗 PRNG，選尾端時整條反轉。PRNG 消耗順序是位元可重現的一部分，C1 起不可再改，否則題庫要升版。`greyOf` 與 `level-decode` 內的灰底計算重複兩行，為守同層不互 import 刻意保留。
