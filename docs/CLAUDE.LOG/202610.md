## 2026-10-24 B3 Solver：計數到 n 即停、節點預算（spec：docs/superpowers/specs/2026-10-24-prime-trail-design.md §5）

- **起因**：plan `docs/superpowers/plans/2026-10-24-prime-trail.md` Task B3（taskboard GAME-5）。題庫生成（C1）的唯一解檢查、進階 greedy 與挑戰計數都靠這支 solver，題庫與測試也用它驗證。

## 2026-10-24 B6 BsModal／BsToast／useConfirm 與 App 掛載（spec：docs/superpowers/specs/2026-10-24-prime-trail-design.md）

- **起因**：plan `docs/superpowers/plans/2026-10-24-prime-trail.md` Task B6（taskboard GAME-8）。C、D 層的過關視窗、看解答／匯出 PDF 確認、「已恢復進度」Toast、「重新開始」確認都要用到 Modal／Toast／Confirm，但 Global Constraints 規定不 import Bootstrap JS，所以要自己寫，只借 Bootstrap 的 class。
- **裁定（使用者）**：無（照 plan 介面實作）。
- **做法**：
  - `BsModal` 用 `v-if` 加 `<Teleport to="body">`，不做淡入淡出動畫：沒有 Bootstrap JS 就沒有 transition 事件可等，`v-if` 讓「關閉 = DOM 消失」可以同步測，清理（body class、keydown listener、焦點歸還）在 `modelValue` 變 false 時同步做完；`closed` 則延到下一個 `nextTick`，等對話框真的從 DOM 移除才 emit，因為 watcher 跑在移除對話框的那次 render 之前（審查第 1 輪的建議）。
  - 用模組層的開啟堆疊（`openStack`）而不是每個 instance 各自切 `modal-open`：疊兩層 Modal（例如過關視窗上再跳確認）時，關掉內層不會把 body 的捲動鎖拿掉，Esc 也只關最上層。堆疊同時決定視覺層級：每個 Modal 開啟時取「目前最上層 + 1」，依層數給 modal 與 backdrop 加 inline z-index（以 Bootstrap 的 1055／1050 為基準，每層 +10）。原因是 Teleport 在掛載時就在 body 放好錨點，DOM 順序跟著掛載順序走；App 層的確認 host 比頁面上的 Modal 早掛載，如果只靠 Bootstrap 固定的 z-index，晚開的確認框反而會被早開的頁面 Modal 蓋住、點不到（審查第 1 輪抓到的問題）。
  - 背景點擊用 `target === currentTarget` 判斷：真實瀏覽器的 `.modal` 疊在 `.modal-backdrop` 上方、會先吃到點擊，所以兩個元素都掛同一個 handler，從對話框內冒泡上來的點擊不算。
  - 初始焦點先找 `[autofocus]`，沒有才找第一個可聚焦元素：不然確認框的焦點會落在標頭的 × 鈕。`BsConfirmHost` 把 autofocus 放在取消鈕，誤按 Enter 不會執行「重新開始」這種破壞性動作。
  - `useToast`／`useConfirm` 是模組層單例，App 只掛一個 host；新的 confirm 進來時，還沒回答的舊請求以 `false` 結束，避免 promise 永遠懸著。`ConfirmRequest.settle()` 做成冪等，host 與呼叫端怎麼重複觸發都只 resolve 一次。
  - 這層不 import i18n（B5 同層、檔案不相交）：按鈕與關閉鈕的 `aria-label` 由呼叫端或 `closeLabel` prop 傳入，預設是英文 `OK`／`Cancel`／`Close`，避免元件內出現 CJK 字串被 B5 的守門測試擋下。D 層接線時再傳 `t('common.*')`。
  - 刻意不動：`main.scss`（modal、toast、close 早就匯入了）、router、views。
- **守門**：測試檔 5 → 7、案數 28 → 54（新增 `BsModal.test.ts` 16 案、`toast-confirm.test.ts` 9 案，涵蓋 plan 列的所有斷言，另外加測疊層 Esc、掛載順序與開啟順序相反時的層級、低層關閉後新開的 Modal 仍在最上層、卸載清理、footer slot、autofocus、新請求取代舊請求）。`pnpm typecheck`、`pnpm test`（7 files／54 tests passed）、`pnpm build` 全綠。
- **流程**：單 agent 在 worktree `task/GAME-8` 實作（範圍小，沒有 fan out），交由主 session 審 diff 合併。
- **踩坑**：一開始的開啟堆疊只用來判斷誰處理 Esc，沒有管視覺層級；審查第 1 輪抓到後改成同時決定 z-index。之後寫疊層 UI 時，要分開驗證「誰收鍵盤」和「誰在最上面」。

## 2026-10-24 GAME-11（C3）useGame 與 useTimer

- **盤面以「整片替換」驅動響應**：Vue 的 `reactive` 不代理 `Uint8Array`，就地寫入 `grid[cell]` 不會觸發 `head`／`conflicts`／`isFull` 重算；因此每次寫入都 `slice()` 一份新陣列再指派給 `state.grid`。100 bytes 的複製成本可忽略，換來 computed 永遠正確，不需要手動 trigger。
- **計時器以 `now()` 差值累加，interval 只負責刷新顯示**：`pause/stop/隱藏` 時立即結算，所以 interval 的 250 ms 粒度不影響最終成績。`elapsedMs` 改為 `customRef`：每次讀取都以 `now()` 即時結算並取整數毫秒，interval 只負責 trigger 讓畫面刷新；如此 `snapshot()` 在兩個 tick 之間存檔也不會少算最多 250 ms，且存進 localStorage 的值不再帶 `performance.now()` 的小數。`running` 表示使用者意圖：分頁隱藏時內部停止累加但 `running` 仍為 true，回到可見即續跑；從未啟動或已暫停的計時器不會因 `visibilitychange` 自行開始。
- **勝負判定只在 `place` 內做**（§7.3：「填滿後若 isSolved → won、timer stop」）：審查指出初版的 `settle()` 在 `won` 後 clear／undo 會退回 `playing` 並重啟計時、以及由存檔恢復時可直接成為 `won`，兩者 plan 與 spec 都未定義，屬實作自創，已移除。恢復狀態照 plan 只有 `playing`／`idle`；過關局的存檔會被刪（§7.6），所以「存檔已是完整解」不是正常路徑，測試鎖定它還原為 `playing` 且不啟錶。第二輪審查指出「won 後仍可改盤面」會讓 `place` 把狀態拉回 `playing` 並重啟已停的計時器、`clear`／`undo` 則讓盤面與 `won` 不一致；改採最保守的做法：`won` 期間 `place`／`clear`／`undo` 一律拒絕（回 false，trail／backspace 經由它們同樣被擋），只有 `reset()` 解鎖。這不新增任何狀態轉移，只是不讓已結算的成績被改動；是否允許過關後繼續玩留待 spec 決定（backlog 草稿）。
- **由存檔恢復時 given 一律以題面為準**：`useProgress` 已負責丟棄不相容存檔（§7.6），這裡再覆寫一次 given 只是防禦；恢復後計時器 `reset(saved.elapsedMs)` 不啟動，等下一次 `place` 才開始（Review Focus 6）。
- **`select()`／`setInputMode()` 只設值、不清 `pending`、不驗格號**：初版自行加了換格／切模式清 `pending`，spec §7.3 未提，審查判為自創而移除；無效格號由 `place` 拒絕即可。`confirmPending()` 失敗（given 格）時保留 `pending`。是否清空待 spec 補述（backlog 草稿）。
- `hint()` 的 `divergedAt` 取「與參考路徑不一致的最小數字」，所在格以 `cellOfNumber`（重複時取最小格號）定位。
- **第三輪：依使用者對 §7.3 的裁定定案，並補齊會抓到錯誤實作的測試**：使用者裁定「過關即鎖盤」（`won` 後所有改盤操作回 false、只有 `reset()` 解鎖、沒有 won→playing）與「`pending` 不因換格或切模式清空」，兩者與前一輪的保守實作一致，所以實作不需改，只把註解改指向 spec，backlog 草稿的三項待裁定（含「存檔已是完整解答」照 plan 處理）一併撤除。審查指出的問題在測試：原本的測試拿掉 `isSolved` 判斷、讓 `state.elapsedMs` 變成靜態值、讓換格清空 `pending`、或讓暫停／停止的計時器因分頁切回可見而重新計時，都仍然全綠，等於這些規則沒有被鎖住。這輪補的每個案例都以「暫時改壞實作、確認該案例轉紅」驗證過，目的在讓 D 層接 PlayView 時，任何違反 §7.3 的改動都會在 `pnpm test` 直接被擋下，而不是靠人工審查記得這些規則。指定模式也補了一路填到勝利的案例，因為勝負判定只寫在 `place` 內，需要證明經 `confirmPending` 進來的路徑同樣會判勝並停錶。

- 「繼續上次」的 `canResume` 以 `progress.has(lastPlayed.levelId, lastPlayed.difficulty)` 判斷（backlog R21）：`lastPlayed()` 回傳原始指標，對應存檔被刪或被 LRU 淘汰時仍可能存在，spec §7.5 要求這時隱藏按鈕。測試涵蓋了「指標還在、存檔不在」的情況。
- 「隨機」只在 ready 時呼叫 `store.randomId()`（backlog R22）；LevelPicker 本來就只在 ready 時渲染，這個檢查是防禦性的。上界跟著 `count`，不寫死 1000，題庫張數改變時不必改這裡。
- `start` 與 `resume` 都導向同一個 `play` 路由，是否恢復進度由 PlayView 決定（spec §6.6、§7.6）。
- 照現狀保留 LevelPicker 欄位空白時就顯示錯誤訊息的行為（R30），沒有改元件。

## 2026-10-25 GAME-21 解答視窗棋盤溢出（spec：docs/superpowers/specs/2026-10-24-prime-trail-design.md §6.1–§6.3、§6.8、§9）

- **起因**：使用者截圖（桌機）顯示解答 BsModal 內的棋盤右側超出 `.modal-content`。`src/styles/board.scss` 的 `--cell` 以 `100vw` 計算，桌機會取上限 48px，棋盤寬 11 × 48 = 528px；但預設 `.modal-dialog` 最寬 500px，body 內容只有約 466px。手機也一樣：modal 的外距加上 body 內距，讓可用寬度比 `100vw - 16px` 窄。修正前實測溢出量：桌機 44px、Pixel 7 16px。
- **裁定（使用者）**：(a) 解答棋盤改依容器寬度算 `--cell`；(b) 解答 modal 用 `size="lg"`。不改 `board.scss`，遊戲頁主棋盤不受影響。
- **做法**：
  - `SolutionView.vue` 的根 `.pt-solution` 設 `container-type: inline-size`，並以 scoped `:deep(.pt-board)` 覆寫 `--cell: clamp(20px, calc(100cqi / 11), 48px)`。棋盤寬度恆為 11 個 `--cell`（10 格加兩條半格外框帶），所以 `100cqi / 11` 剛好等於容器寬。棋盤原本就是 `width: max-content; margin-inline: auto`，所以會置中。這個覆寫只套用在解答視窗內，遊戲頁的主棋盤繼續用 `board.scss` 依視窗寬計算。
  - 下限為什麼從 30px 降到 20px：用 Playwright 量容器（`.pt-solution`）實際寬度，320px 寬時 270px、375px 時 325px、Pixel 7（412px）時約 362px。375px 的手機就已經小於 330px（30 × 11），30px 下限在常見手機寬度會溢出。降到 20px 後，最小 220px 仍可放進 320px 手機的 270px 容器。實際 cell 寬度：320px 約 24.5px，375px 約 29.5px，數字仍然可讀（字級也以 `--cell` 等比縮放）。
  - `PlayView.vue` 的解答 `<BsModal>` 加 `size="lg"`。視窗寬 ≥ 992px 時 dialog 為 800px，body 內容 766px，棋盤以 48px（528px）完整顯示；576–991px 時 dialog 仍是 500px，cell 會縮成約 42px，不溢出。
- **守門**：新增 `e2e/09-solution-layout.spec.ts`，在 desktop 與 mobile project 斷言解答棋盤的左右緣都落在 `.modal-content` 內（容許 1px），在「參考解」與「你的解」兩個視圖都檢查。修正前兩個 project 都失敗（桌機右緣 935 > 891，手機右緣 421 > 405），修正後通過。`pnpm test:e2e` 22 passed、1 skipped（03 在 desktop 依設計跳過）。DoD 三條全綠。
- **流程**：單一 agent 在 worktree 分支 `fix/GAME-21` 實作，基底 c56f45f。
- **遺留**：320px 寬時遊戲頁主棋盤仍是 330px（`board.scss` 下限 30px），比視窗寬，這不在本任務範圍內，寫進 backlog 草稿。
