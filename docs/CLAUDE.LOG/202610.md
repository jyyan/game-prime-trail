## 2026-10-24 B3 Solver：計數到 n 即停、節點預算（spec：docs/superpowers/specs/2026-10-24-prime-trail-design.md §5）

- **起因**：plan `docs/superpowers/plans/2026-10-24-prime-trail.md` Task B3（taskboard GAME-5）。題庫生成（C1）的唯一解檢查、進階 greedy 與挑戰計數都靠這支 solver，題庫與測試也用它驗證。

- **做法**：

## 2026-10-24 B6 BsModal／BsToast／useConfirm 與 App 掛載（spec：docs/superpowers/specs/2026-10-24-prime-trail-design.md）

- **起因**：plan `docs/superpowers/plans/2026-10-24-prime-trail.md` Task B6（taskboard GAME-8）。C、D 層的過關視窗、看解答／匯出 PDF 確認、「已恢復進度」Toast、「重新開始」確認都要用到 Modal／Toast／Confirm，但 Global Constraints 規定不 import Bootstrap JS，所以要自己寫，只借 Bootstrap 的 class。
- **裁定（使用者）**：無（照 plan 介面實作）。
- **做法**：
  - `BsModal` 用 `v-if` 加 `<Teleport to="body">`，不做淡入淡出動畫：沒有 Bootstrap JS 就沒有 transition 事件可等，`v-if` 讓「關閉 = DOM 消失」可以同步測，清理（body class、keydown listener、焦點歸還）在 `modelValue` 變 false 時同步做完；`closed` 則延到下一個 `nextTick`，等對話框真的從 DOM 移除才 emit，因為 watcher 跑在移除對話框的那次 render 之前（審查第 1 輪的建議）。
  - 用模組層的開啟堆疊（`openStack`）而不是每個 instance 各自切 `modal-open`：疊兩層 Modal（例如過關視窗上再跳確認）時，關掉內層不會把 body 的捲動鎖拿掉，Esc 也只關最上層。堆疊同時決定視覺層級：每個 Modal 開啟時取「目前最上層 + 1」，依層數給 modal 與 backdrop 加 inline z-index（以 Bootstrap 的 1055／1050 為基準，每層 +10）。原因是 Teleport 在掛載時就在 body 放好錨點，DOM 順序跟著掛載順序走；App 層的確認 host 比頁面上的 Modal 早掛載，如果只靠 Bootstrap 固定的 z-index，晚開的確認框反而會被早開的頁面 Modal 蓋住、點不到（審查第 1 輪抓到的問題）。
  - 背景點擊用 `target === currentTarget` 判斷：真實瀏覽器的 `.modal` 疊在 `.modal-backdrop` 上方、會先吃到點擊，所以兩個元素都掛同一個 handler，從對話框內冒泡上來的點擊不算。
  - 初始焦點先找 `[autofocus]`，沒有才找第一個可聚焦元素：不然確認框的焦點會落在標頭的 × 鈕。`BsConfirmHost` 把 autofocus 放在取消鈕，誤按 Enter 不會執行「重新開始」這種破壞性動作。
  - `useToast`／`useConfirm` 是模組層單例，App 只掛一個 host；新的 confirm 進來時，還沒回答的舊請求以 `false` 結束，避免 promise 永遠懸著。`ConfirmRequest.settle()` 做成冪等，host 與呼叫端怎麼重複觸發都只 resolve 一次。
  - 這層不 import i18n（B5 同層、檔案不相交）：按鈕與關閉鈕的 `aria-label` 由呼叫端或 `closeLabel` prop 傳入，預設是英文 `OK`／`Cancel`／`Close`，避免元件內出現 CJK 字串被 B5 的守門測試擋下。D 層接線時再傳 `t('common.*')`。
  - 刻意不動：`main.scss`（modal、toast、close 早就匯入了）、router、views。
- **守門**：測試檔 5 → 7、案數 28 → 54（新增 `BsModal.test.ts` 16 案、`toast-confirm.test.ts` 9 案，涵蓋 plan 列的所有斷言，另外加測疊層 Esc、掛載順序與開啟順序相反時的層級、低層關閉後新開的 Modal 仍在最上層、卸載清理、footer slot、autofocus、新請求取代舊請求）。`pnpm typecheck`、`pnpm test`（7 files／54 tests passed）、`pnpm build` 全綠。
- **流程**：單 agent 在 worktree `task/GAME-8` 實作（範圍小，沒有 fan out），交由主 session 審 diff 合併。
- **踩坑**：一開始的開啟堆疊只用來判斷誰處理 Esc，沒有管視覺層級；審查第 1 輪抓到後改成同時決定 z-index。之後寫疊層 UI 時，要分開驗證「誰收鍵盤」和「誰在最上面」。

## 2026-10-24 C1 題庫生成腳本（spec：docs/superpowers/specs/2026-10-24-prime-trail-design.md）

- **起因**：taskboard GAME-9（plan Task C1）。D4 要在本機長時間跑出 1000 張凍結題庫，需要一支可中斷續跑、結果與分批方式無關、組裝前自驗的生成腳本。
- **裁定（使用者）**：無（照 plan 與 spec §4 的規劃者決定）。
- **做法**：

  - **greedy 的 rng 沿用該候選 backbite 之後的狀態**（plan「用該候選的 rng 洗牌順序」）。好處是 `seed` 一個值就能完整重建：`createRng(seed)` → 重跑 backbite → rng 狀態就是 greedy 起點。`--recompute h,c` 因此不必另存 rng 狀態，`recomputeRow` 還會比對重建出的路徑，路徑對不上（backbite 參數或演算法漂移）就拒絕。
  - **`--recompute` 的結果必須等於用新參數從零生成**（spec §4.3：同 generator＋masterSeed 必產出位元相同的 `levels.json`；審查第 1 輪指出初版只重算選中候選的 `c` 而不重選，調 `challengeBudget` 後續跑與全新生成會挑到不同路徑）。現在重算 `c` 會把 meta 記下的每個候選從 seed 重建、全部重數、重新挑選；挑選換人時即使沒要求 `h` 也重跑 greedy。不在重算範圍內的參數（路徑與 easy 篩選相關的 `masterSeed`、`backbiteSteps`、`edgeExtraMax`、`easyBudget`、`candidates`、`maxAttemptsPerLevel`，以及沒要求重算那段的預算）必須與該行建立時相同，否則拒絕、要求整張重生；為此每行 meta 多存一份 `config` 快照。測試以「重算結果 == 新參數 `generateLevel`」逐欄比對（c、h、h＋c 三種），並用一個確定會換候選的案例（id 5）確保測試真的走到重選。
  - `c` 的語意：解數達 cap 記 cap（表示 ≥ CAP），預算用盡記 `null`；挑選時 `null` 排最後、平手取 attempt 小者（候選本來就依 attempt 排序，嚴格小於才換即可）。
  - meta 的「完成」以 `generator` 字串**且** `config` 快照都與目前 `gen-config.ts` 相同為準：改了參數（就算忘了升版本字串）舊行也會視為未完成而重生，組裝也只用當前參數的行，避免新舊參數混在同一份 `levels.json`。`--recompute` 吃任何版本的既有行，由上一條的檢查決定能否沿用。
  - `appendMeta` 寫入前若檔尾不是換行（上次中斷在半行），先補一個換行，否則新行黏在殘行後面、兩張一起變壞行。
  - `verifyLevelFile` 先用 `parseLevelFile` 做結構檢查，再對每張做提示一致、`popcount(h) ≥ advFloor`、相鄰 given 距離／奇偶可達、easy 與 advanced 唯一（solver 預算與生成時相同，生成時通過的不會在驗證時因預算不同而誤判）。

## 2026-10-24 GAME-10（C2）棋盤元件與 board.scss

- **事件委派集中在 `.pt-board`**：`BoardCell` 無 emits，`GameBoard` 用 `closest('[data-cell]')` 找格，避免 100 個 listener（§6.2）。拖曳以 `setPointerCapture` 綁在棋盤本身，`pointermove` 改用 `document.elementFromPoint` 找格，因為 capture 後 `e.target` 恆為棋盤。
